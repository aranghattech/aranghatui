# ADR-0023: Server-side rendering — hydrate modules per tier, hydratable client behind the `artui-ssr` condition

**Status:** Accepted (2026-09-16, Phase 8)

## Context

Phase 8 requires SSR / hydration verification for React, Vue and Angular hosts. Stencil provides it: a `dist-hydrate-script` output target builds a Node "hydrate app" whose `renderToString()` renders every component of the project into declarative shadow DOM (`<template shadowrootmode="open">` with the component's styles inlined), and the client runtime, when compiled with that target present, adopts a server-rendered shadow root instead of rendering a second copy.

Two things about our setup do not fit the default story:

1. **Five independent Stencil projects.** A hydrate app only knows its own tier. `art-login` renders `art-input` and `art-button` inside its shadow root; a page mixes tiers freely. Running the tiers' `renderToString` one after another does not work either: the serializer drops a `<template>` child of any element that already carries a hydrate id, so an outer pass erases what an inner pass produced.
2. **N1.** The client-side hydration code Stencil adds when a hydrate target exists costs about 3 kB gzip *per tier runtime* (base: 9.28 → 12.21 kB) and takes the landing-page reference from 14.09 to 17.03 kB — over its 15 kB budget — for every consumer, including the SPAs that never render on a server.

## Decision

- **One hydrate app for every tier: `@aranghat/hydrate`.** `packages/hydrate` collects the five tiers' component sources (`scripts/collect.mjs` → `src-all/<tier>`) and compiles them into a single Stencil hydrate app, so `art-login` and the `art-input` it renders inside its shadow root are rendered by the same pass. Running the tiers' own hydrate apps one after another cannot do this: Stencil's discovery walk only follows light-DOM children, so a lower tier never sees elements inside another tier's shadow root, and every extra pass re-annotates the text nodes of the earlier ones. The package's entry wraps Stencil's `renderToString` / `hydrateDocument` / `streamToString` to fill the gaps in the mock document that components rely on (`toggleAttribute`, `replaceChildren`); `@aranghat/hydrate/stencil` is the raw app. Peers and runtime deps are bundled: Node has no bundler in front of it.
- **The default client stays lean.** Each tier is built twice from the same sources: `dist/components` without a hydrate target, and — with `ARTUI_SSR=1` — `dist/components-ssr` (the tier-only hydrate app that build has to produce to enable client hydration is deleted). The package `exports` map serves `dist/components-ssr` under the **`artui-ssr` resolve condition** for every entry (`.`, `./<component>`, `./dist/components/*`); everything else resolves to the lean build. An SSR host adds one line to its bundler (Vite / Nuxt `resolve.conditions`, Next.js `resolve.conditionNames`, Angular `conditions`) and gets the client that adopts server-rendered shadow roots. The framework wrappers need no change: they import the tier by package name and follow the condition of the app that bundles them.
- **Framework bindings are generated by the hydrate build** (the React target requires a hydrate target in the same build once `hydrateModule` is set): each tier's React package gets `<tag>.server.ts` wrappers exported as `@aranghat/<tier>-react/next` for React Server Components (the client entry keeps `'use client'`), each Vue package's proxies branch on `globalThis.window`; both render through `@aranghat/hydrate`, an optional peer of every `-react` / `-vue` package. Binding metadata (`v-model`, `ngModel`) moved to `@artui/stencil-config/models` so the tier builds (Angular) and the hydrate build read one source. Angular has no output-target support: the server post-processes Angular's HTML with `hydrateDocument`, and only attribute-bound inputs reach the server markup (documented in the SSR guide).
- **Components are written to survive a server document:** no `:scope` selectors (`child` / `children` in `@aranghat/primitives/dom`), no `:dir()` in `matches()` (`isRtl`), observers and lazy registration guarded, floating positioning tolerant of a document without layout.

## Consequences

- SSR is opt-in and free for everyone else: lean runtime and reference budgets unchanged; the hydratable runtime chunk is tracked by size-limit (≤ 20 kB) so it cannot drift silently.
- Build time grows by one Stencil build per tier (~5–10 s each) plus the all-tier hydrate build (~40 s); tier packages roughly double on disk (irrelevant to the client bundle).
- The SSR suite (`tests/ssr`, in the gate) renders every sandbox sample in Node and, for one example per component, loads the result in Chromium with the `artui-ssr` client: identical pixels before and after hydration, no duplicated content, no page error.
- Overlays that are `open` at load render closed on the server and open on hydration; light-DOM components (ADR-0021) render as plain markup.
- Revisit if Stencil ever makes client-side hydration tree-shakable or lets a hydrate app descend into foreign shadow roots (then the per-tier apps could return).
